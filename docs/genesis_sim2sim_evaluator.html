Genesis sim2sim evaluator

How scripts/rsl_rl/evaluate_sim2sim_genesis.py runs exported ONNX policies from Isaac Lab inside Genesis, reconstructs Isaac-style observations, and applies target-environment actuator dynamics.

What this script does

This script is a Genesis-based sim2sim evaluator. It takes an ONNX policy exported from this repo (via scripts/rsl_rl/play.py or MotionOnPolicyRunner), loads it with ONNX Runtime, and rolls it out in a Genesis simulation of the G1 humanoid.

The goal is to test whether a policy trained in Isaac Lab still tracks a reference motion when the low-level actuator model and simulator change. In your Delta-A experiments, Genesis plays the role of the target environment via perturbed Kp/Kd gains in an explicit PD torque loop.

Related docs: project_understanding.md, delta_action_finetuning_implementation.md.

Big picture

Think of the evaluator as three layers:

  1. Policy runtime — ONNX inference + metadata from export
  2. Isaac-compatible logic — observation construction and action post-processing
  3. Genesis physics loop — PD torques, optional domain randomization, metrics, video, trajectory logging
ONNX policy | +--- actions --------------------> action post-process --> joint target | +--- reference motion (joint/body) -> observation builder ^ | Genesis robot state ------------------------+ joint target --> PD torques --> scene.step() --> new robot state | +--> metrics / video / NPZ

At each control step the script:

  1. Builds an observation from Genesis state + reference motion.
  2. Runs the ONNX policy.
  3. Converts the policy action into a joint target.
  4. Applies PD torques in Genesis for several physics substeps.
  5. Reads the new state, logs metrics, and repeats.

The ONNX policy is more than an actor

The exported policy is a motion-tracking bundle, not just a neural network mapping obs → action.

Inputs

  • obs — flattened policy observation vector
  • time_step — index into the embedded reference motion

Outputs

  • actions — policy action
  • joint_pos, joint_vel
  • body_pos_w, body_quat_w, body_lin_vel_w, body_ang_vel_w

The reference motion tensors are baked into the ONNX at export time from the motion used during export. Genesis uses them as the reference trajectory for both observations and metrics.

So the policy plays two roles:

  • Controller — outputs actions
  • Reference motion server — outputs reference states at each time_step

That is why _fetch_reference_batch() can call the policy with zero observations and still recover reference joint/body states for a given timestep.

Startup (__init__)

When you construct Sim2SimEvaluatorGenesis, it performs these setup steps.

A. Load policy metadata

From ONNX metadata (attach_onnx_metadata) it reads:

  • joint names and default joint positions
  • action scales
  • observation term names and history lengths
  • tracking body names and anchor body
  • nominal Kp/Kd from Isaac export

Then it perturbs Kp/Kd for the target environment. The current implementation uses a fixed RNG seed (_EVAL_KP_KD_PERTURB_RNG_SEED = 913571) and applies a Gaussian-scaled perturbation: 

joint_stiffness_final = Kp_orig * (1 + 0.27 * N(0, 1))
joint_damping_final   = Kd_orig * (1 + 0.27 * N(0, 1))

This Kp/Kd perturbation seed is separate from --seed / evaluation seed used for obs noise and DR.

B. Create ONNX Runtime session

Runs inference on CPU or CUDA (--policy_device).

C. Build Genesis scene

  • ground plane
  • G1 URDF robot (--urdf_file)
  • optional white reference marker spheres (--show_reference)
  • optional camera for video (--record_video)
  • optional parallel envs (--num_envs)

D. Map joints and links

Metadata joint names are mapped to Genesis DOF indices. Metadata body names are mapped to Genesis links for observation construction and metrics.

E. Optional motion file

--motion_file is only required if the policy observation includes motion_joint_action (open-loop delta policies). Standard finetuned tracking policies do not need it for reference motion, because reference states come from the ONNX itself.

F. Infer rollout length

The script inspects the ONNX graph to infer embedded reference motion length, then sets:

max_steps = reference_motion_length − start_timestep

One control step

The core loop lives in evaluate():

for t_step in range(max_steps):
    ref_step = start_timestep + t_step
    policy_out = run_policy(obs, ref_step)
    action = policy_out["actions"]
    ref = policy_out joint/body reference tensors

    joint_target = compute_joint_target(action, ref_step)
    maybe_apply_interval_push(t_step)
    step_simulation(joint_target)

    state = extract_state()
    compute metrics / logging

    last_action = action
    obs = build_observation(state, ref_next, ref_step + 1)

Step 1 — Policy inference

_run_policy(obs, time_step) returns actions plus reference motion tensors.

Step 2 — Action post-processing

For standard tracking policies:

q_des = q_default + action_scale ⊙ a

For open-loop delta policies that include motion_joint_action in the observation:

a_processed = a_policy + a_motion(time_step)
q_des = q_default + action_scale ⊙ a_processed

Step 3 — Low-level control in Genesis

Unlike Isaac’s implicit actuator, Genesis uses an explicit PD torque law repeated for sim_decimation = control_dt / sim_dt substeps (default 20):

τ = Kp ⊙ (q_des − q) − Kd ⊙ q̇

Then robot.control_dofs_force(τ) and scene.step().

Step 4 — Read robot state

Joint positions/velocities and body poses/velocities are read back from Genesis links.

Step 5 — Build next observation

Isaac-style observation terms are reconstructed and concatenated in metadata order.

Observation building

_build_observation() manually reconstructs the Isaac Lab policy observation group. Supported terms and dimensions are hardcoded in _build_term_dims():

TermMeaning
command[ref_joint_pos, ref_joint_vel]
motion_anchor_pos_bAnchor position error in robot frame
motion_anchor_ori_bAnchor orientation error (6D rotation columns)
base_lin_velRoot linear velocity in body frame

joint_velJoint velocities

motion_joint_actionOptional; for delta open-loop policies

Additional behavior:

  • observation history stacks via per-term deques
  • optional uniform noise on selected terms (--add_noise, default on)
  • strict dimension check against ONNX input size

Episode reset

At the start of each rollout:

  1. Fetch reference state at start_timestep from ONNX.
  2. Place the robot at the reference root pose and joint positions.
  3. Zero velocities.
  4. Reset observation history and last_action.
  5. Optionally apply domain randomization for this rollout.

Domain randomization

With --domain_randomization (default on), Genesis attempts to mirror Isaac DR:

  • randomized default joint offsets
  • randomized friction / restitution
  • randomized base COM
  • interval pushes on root DOFs

Much of the extra code in this file exists to handle Genesis API/version differences for these randomization calls.

Metrics and termination

Each step computes Isaac-style tracking errors and reward-like terms:

  • anchor position / orientation error
  • body position / orientation error
  • joint position / velocity error
  • exponential tracking reward components

Early termination checks include:

  • anchor height mismatch
  • anchor orientation mismatch via projected gravity difference

With --compute_metrics, the script also reports:

  • MPJPE global and local
  • velocity distance
  • acceleration distance

A rollout is counted as successful if the env survives until near the end of the motion (max_steps − 5).

Important design choices

1. Reference motion comes from ONNX, not --motion_file.
The motion file is only needed for policies whose observation includes motion_joint_action. The tracking reference itself is embedded in the exported ONNX.
2. Target env = perturbed Kp/Kd in Genesis PD loop.
This is where your gain-shift experiment lives. It is separate from Isaac training dynamics.
3. Only the base policy is deployed here.
There is no delta-policy branch in this evaluator. That matches the intended deployment story for Delta-A finetuned checkpoints.
4. Actuator model differs from Isaac.
Isaac uses implicit actuators; Genesis uses explicit PD torques each substep. Even with matched Kp/Kd numbers, the resulting closed-loop dynamics may not match exactly.
5. Batch handling.
The script supports vectorized Genesis envs, but ONNX may fall back to per-env inference if the model was exported with fixed batch size 1.

Minimal mental model

If you ignore logging, DR, and metrics, the evaluator reduces to:

while t < motion_length:
    obs = f(genesis_state, reference_motion[t])
    a, ref = onnx_policy(obs, t)
    q_des = q_default + scale * a
    tau = Kp * (q_des - q) - Kd * qdot
    genesis.step(tau)
    t += 1

Everything else — quaternion math, DR, MPJPE, NPZ export, video — wraps around this core control loop.

Relation to Delta-A sim2real

In the Delta-A pipeline, Isaac Lab is the source simulator and Genesis is the target simulator. Open-loop delta training learns a helper that makes the assisted source environment behave more like the target. Finetuning then trains the base policy under those assisted dynamics.

This Genesis evaluator tests the deployed finetuned base policy alone under perturbed actuator gains. It does not run the frozen delta policy at inference time. Whether transfer succeeds therefore depends on how well the delta-assisted source dynamics matched the true Genesis target dynamics during finetuning.
