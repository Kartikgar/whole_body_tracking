Motion command alignment

Intuition for re-rooting and re-yawing in MotionCommand._update_command (body_pos_relative_w, body_quat_relative_w).

The problem

The dataset gives you one articulated pose per timestep: joint angles and rigid-body poses for a skeleton. Those poses live in whatever world frame the exporter used (often a moving origin that follows the character in the recording).

In simulation, your robot sits on a tiled floor at some map location and may slowly drift sideways or yaw under control noise, disturbances, or an open-loop policy. If you asked the policy “match every body to the NPZ literal world XYZ every frame,” small root drift would look like catastrophic whole-body pose error—even when the limbs still match the demonstration relative to the character.

So we split concerns: anchor terms penalize gross root mismatch explicitly; articulated matching uses a transformed copy of the reference that rides on today’s root alignment.

What we want intuitively

  • Same shape as the clip — Preserve the kinematic pose relative to the demonstration root (bone layout).
  • Couple XY to the simulated root — Keep horizontal placement tied to where the robot actually is so drifting does not inflate limb errors artificially.
  • Preserve clip height semantics on Z — Vertical component of the new origin tracks the NPZ anchor height (hybrid).
  • Match heading in yaw only — Rotate the whole reference skeleton horizontally so demonstrations recorded facing “north” line up when the simulation faces northeast, without baking tilt from a bent torso into “heading.”

Rigid-body picture

Treat each timestep like a rigid constellation of rigid bodies—the motion skeleton—then apply one world transform (ΔR, t):

Rotation (ΔR).   quaternion product: ΔR = (robot yaw about world ↑) × inverse(clip yaw about world ↑)

Translation hybrid (vector t).   t = (xrobot, yrobot, zclip anchor)

positions   p′i = t + ΔR · (pclipi − pclipanchor)

orientations   R′i = ΔR · Rclipi

That is literally “express every NPZ body relative to the clip anchor in world axes, rotate by heading delta, translate so the synthetic root sits at t”—nothing per-link fancier than that.

delta_pos_w           →  t replicated per-body for tensors only

body_pos_relative_w   →  p′ᵢ in world. Still Cartesian world;
                           "_relative" ≠ link-local; means aligned clip pose.

anchor_pos_w          →  raw NPZ anchor (goal anchor in debug viz)
robot_anchor_pos_w    →  simulated anchor body pose

Why debug visuals can confuse

Body goal markers often plot body_pos_relative_w (“aligned” targets), while the anchor goal marker plots raw anchor_pos_w. If the simulated root slips away from the literal NPZ root, the anchor spheres separate—the body frames can still hug the limbs because alignment explicitly uses the robot XY and yaw every step.

Why headings use a designated body

Yaw from anchor_body_name (often torso) mixes pitch when the torso leans forward. The code prefers relative_heading_body_name (defaulting to pelvis/root) stripped to yaw_quat: pure azimuth about world up, stabler horizontal alignment.

Takeaway

Re-rooting and re-yawing are not tricks to confuse the reward—they are how you define a consistent tutorial frame for the articulated reference: horizontal root follows the simulator, clip height informs vertical origin, headings match in yaw, and the articulated pose from the NPZ arrives as plausible Cartesian targets (*_relative_w) you can subtract from simulated body world positions.
